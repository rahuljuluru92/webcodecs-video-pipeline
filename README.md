# WebCodecs Video Pipeline

A browser-native video processing and interactive playback pipeline built directly on the [WebCodecs API](https://developer.mozilla.org/en-US/docs/Web/API/WebCodecs_API), Canvas, and Web Workers — no server-side transcoding, no video-player framework. It demuxes an MP4 file, decodes it with `VideoDecoder`, and renders it to a canvas with:

- Adaptive frame buffering/prefetching that sizes itself to measured decode speed
- Frame-accurate keyframe-based seeking, a scrubbing UI, variable playback speed, and reverse playback
- The entire decode/render pipeline running inside a Web Worker, off the main thread
- A bounded LRU frame cache so scrubbing a long file doesn't grow memory without limit

This is a playback/processing pipeline, not a video editor — there's no encoding, export, or timeline-effects UI, by design.

## What's actually verified here

This README states only what was actually measured and tested for this project, not what "should" work. In particular:

- **Only tested in one Chromium-based browser** (see [Browser support](#browser-support) below). No Firefox/Safari testing has been done.
- **Only tested against synthetic H.264-in-MP4 fixtures** generated by ffmpeg (see [Test fixtures](#test-fixtures)) — not real-world footage, not other codecs.
- Every benchmark number in this file is a real, reproducible measurement recorded during development (see `DECISIONS.md`), not an estimate.

## Setup

```bash
npm install
npm run dev
```

Open the printed local URL, choose an MP4 file, and use the Play/Pause, Reverse, speed selector, and scrubber controls.

Requires Node.js (developed and tested with **v23.10.0** / npm **10.9.2**).

### Building for production

```bash
npm run build
npm run preview
```

Vite automatically code-splits the Web Worker (which holds the entire decode/render pipeline) into its own chunk, separate from the small main-thread bundle.

## Browser support

WebCodecs support varies significantly across browsers and was not assumed to be universal. This project was built and tested exclusively against:

| Context | Browser | Notes |
|---|---|---|
| Manual testing throughout development | `Chrome/148.0.7778.280` | Claude Code's bundled Chromium-based preview browser (via `navigator.userAgent`) |
| Automated end-to-end tests (Playwright) | `Google Chrome for Testing 151.0.7922.34` | Playwright `@playwright/test` v1.62.1's bundled Chromium |

**Firefox and Safari were never tested against this project**, and no claim is made about whether it works there. The app does feature-detect for `VideoDecoder`, `Worker`, and `OffscreenCanvas` on load and shows an explicit message if any are missing, rather than failing silently or half-working.

## How the pipeline is built

- **`src/mp4-demuxer.ts`** — demuxes an MP4 `ArrayBuffer` via [mp4box.js](https://github.com/gpac/mp4box.js) into a `VideoDecoderConfig` and an array of `EncodedVideoChunk`s (no browser ships a native MP4 demuxer, so this dependency is required for a WebCodecs pipeline at all).
- **`src/frame-buffer.ts`** — a generic, cancellable FIFO queue used to decouple decoding from rendering.
- **`src/prefetch-controller.ts`** — pure logic that sizes the buffer's target depth from a one-time measured decode-fps vs. the file's nominal playback fps (floor 6 frames, ceiling 90).
- **`src/keyframe-index.ts`** — pure keyframe/GOP-boundary lookup logic backing seeking and reverse playback.
- **`src/gop-decoder.ts`** — decodes one bounded GOP range with a fresh decoder; shared by seeking and reverse playback.
- **`src/frame-cache.ts`** — a generic, capacity-bounded LRU cache.
- **`src/seekable-player.ts`** — ties all of the above together: `play()`/`pause()`/`seekTo()`/`setPlaybackRate()`/`setDirection()`, keyframe-based seeking with an LRU seek-frame cache, and GOP-buffered reverse playback.
- **`src/video-worker.ts`** — runs `SeekablePlayer` entirely inside a dedicated Worker against a transferred `OffscreenCanvas`, so demuxing, decoding, and rendering never touch the main thread.
- **`src/worker-video-player.ts`** / **`src/worker-protocol.ts`** — the main-thread proxy and shared message types for talking to the worker.
- **`src/main.ts`** — wires the UI controls to `WorkerVideoPlayer`.

## Testing

```bash
npm run test        # unit tests (Vitest) + browser tests (Playwright), in that order
npm run test:unit   # Vitest only — pure logic: FrameBuffer, AdaptivePrefetchController, KeyframeIndex, FrameCache
npm run test:e2e    # Playwright only — real WebCodecs decode/render/seek in an actual browser
```

34 Vitest unit tests cover the pure, WebCodecs-independent logic (buffer backpressure/cancellation, adaptive buffer-depth math, keyframe/GOP lookups, LRU cache eviction). 7 Playwright tests run against real browser WebCodecs decoding: full-file playback for both fixtures, seek-lands-on-the-correct-frame (forward and backward), reverse playback producing monotonically decreasing timestamps, cache-hit behavior on repeat seeks, and bounded memory growth across many seeks. All 41 tests pass as of the last stage.

Playwright needs its bundled Chromium installed once: `npx playwright install chromium`.

## Test fixtures

No real-world sample footage was available while building this project, so all test fixtures are synthetic, fully reproducible ffmpeg output (SMPTE-style `testsrc` pattern + a tone), generated on demand rather than committed to git (`test-media/` is gitignored — regenerate with the commands below).

| File | Resolution | Duration | Profile | Purpose |
|---|---|---|---|---|
| `short_640x360_10s.mp4` | 640×360 | 10s | H.264 Constrained Baseline | Fast iteration / baseline correctness |
| `long_1920x1080_60s.mp4` | 1920×1080 | 60s | H.264 High | Higher-resolution decode throughput |
| `long_form_640x360_900s.mp4` | 640×360 | 900s (15 min) | H.264 Constrained Baseline | Long-form memory/eviction benchmark |

Regenerate all three:

```bash
mkdir -p test-media

ffmpeg -f lavfi -i "testsrc=duration=10:size=640x360:rate=30" \
  -f lavfi -i "sine=frequency=440:duration=10" \
  -c:v libx264 -pix_fmt yuv420p -profile:v baseline -level 3.0 -g 30 \
  -c:a aac -shortest test-media/short_640x360_10s.mp4

ffmpeg -f lavfi -i "testsrc=duration=60:size=1920x1080:rate=30" \
  -f lavfi -i "sine=frequency=220:duration=60" \
  -c:v libx264 -pix_fmt yuv420p -profile:v high -level 4.0 -g 30 \
  -c:a aac -shortest test-media/long_1920x1080_60s.mp4

ffmpeg -f lavfi -i "testsrc=duration=900:size=640x360:rate=30" \
  -f lavfi -i "sine=frequency=330:duration=900" \
  -c:v libx264 -pix_fmt yuv420p -profile:v baseline -level 3.0 -g 30 \
  -c:a aac -shortest test-media/long_form_640x360_900s.mp4
```

All three use a keyframe interval of 30 (`-g 30`, one keyframe/GOP boundary per second at 30fps). Only H.264-in-MP4 has been generated and tested; the demuxer/decoder-config code path also handles HEVC/VP9/AV1 generically (it reads whichever of `avcC`/`hvcC`/`vpcC`/`av1C` is present), but that path is unverified — no fixtures in those codecs have been tried.

## Measured benchmarks

All numbers below are real measurements taken during development (Claude Code Browser pane, `Chrome/148.0.7778.280`), recorded verbatim in `DECISIONS.md` alongside full methodology notes. None are estimates.

### Decode throughput and time-to-first-frame (adaptive buffering)

| Fixture | Decode throughput | Time to first frame | Adaptive buffer target |
|---|---|---|---|
| `short_640x360_10s.mp4` | 1764.7 fps | 143 ms | 90 frames (clamped to max) |
| `long_1920x1080_60s.mp4` | 1016.9 fps | 103 ms | 90 frames (clamped to max) |

Both fixtures decode at 30-60x real-time on the test hardware — read this as "this hardware/codec/synthetic-content combination," not a general H.264 decode-speed claim. Both clips played back with zero stalls and zero dropped frames.

### Seek latency (keyframe-based, forward and reverse)

| Fixture | Direction | Sample seeks | Latency range |
|---|---|---|---|
| `short_640x360_10s.mp4` | Forward | 2.00s, 5.00s, 9.00s | 23.7-32.1 ms |
| `short_640x360_10s.mp4` | Reverse | 3.00s, 1.00s, 7.00s | 29.7-31.6 ms |
| `long_1920x1080_60s.mp4` | Forward | 10.00s, 30.00s, 55.00s | 32.2-39.1 ms |
| `long_1920x1080_60s.mp4` | Reverse | 20.00s, 5.00s, 45.00s | 35.3-38.0 ms |
| `long_form_640x360_900s.mp4` | Both | spread across 900s | ~30 ms (unchanged) |

Every seek landed exactly on the requested frame. Latency is dominated by decoding one full GOP (≤30 frames) with a fresh decoder, not by resolution or file duration — a seek on the 900-second fixture is no slower than one on the 10-second fixture.

### Main-thread blocking, before vs. after moving to a Worker

Measured as cumulative `CanvasRenderingContext2D.prototype.drawImage` execution time on the main thread across a full playthrough (the Long Tasks API recorded zero >50ms tasks in *either* architecture, since WebCodecs decode dispatch doesn't block the calling thread by design — `drawImage` is the real, attributable per-frame main-thread cost).

| Fixture | Before (main-thread render) | After (Worker + OffscreenCanvas) |
|---|---|---|
| `short_640x360_10s.mp4` (300 frames) | 92.0 ms | **0.0 ms** (0 calls observed) |
| `long_1920x1080_60s.mp4` (1800 frames) | 430.3 ms | **0.0 ms** (0 calls observed) |

The "after" zero is structural, not a rounding artifact: the worker's rendering calls execute in a separate JS realm the main-thread instrumentation can't observe, which is the same reason the cost is actually eliminated from the main thread, not just hidden from this measurement technique.

### Long-form memory: bounded (LRU cache) vs. unbounded

Measured by issuing many `seekTo()` calls spread across the full 900-second long-form fixture and sampling the live open-`VideoFrame` count after each one — run twice with the identical code path, differing only in the seek-cache's capacity parameter (120, the real default, vs. 1,000,000, simulating the eviction policy switched off).

| Seeks issued | With eviction (120-frame cache) | Without eviction |
|---|---|---|
| 200 | **120** | 6,000 |
| 400 | **120** (unchanged) | 12,000 (doubled) |

With the eviction policy active, memory is flat regardless of session length. Without it, memory grows exactly linearly with usage, with no ceiling — the failure mode a real long-form scrubbing session would hit.

## Known limitations

- No audio playback — only the video track is demuxed/decoded (the pipeline explicitly ignores audio tracks; this was in scope from the start, not a regression).
- Single video track only; files with multiple video tracks use the first one found.
- Firefox/Safari are untested (see [Browser support](#browser-support)).
- Codecs other than H.264 are unverified (see [Test fixtures](#test-fixtures)).
- The seek/frame cache is scoped to `seekTo()` only — continuous forward/reverse playback doesn't use it, since it visits each frame position once, in order, with no repeat-access pattern for a cache to help with (see `DECISIONS.md`, Stage 5).
