# WebCodecs Video Pipeline

A browser-native video processing and interactive playback pipeline built directly on the [WebCodecs API](https://developer.mozilla.org/en-US/docs/Web/API/WebCodecs_API), Canvas, and Web Workers — no server-side transcoding, no video-player framework. It demuxes an MP4 file, decodes it with `VideoDecoder`, and renders it to a canvas with:

- Adaptive frame buffering/prefetching that sizes itself to measured decode speed
- Frame-accurate keyframe-based seeking, a scrubbing UI, variable playback speed, and reverse playback
- The entire decode/render pipeline running inside a Web Worker, off the main thread
- A bounded LRU frame cache so scrubbing a long file doesn't grow memory without limit
- An optional box-blur filter: YUV→RGB conversion + blur compiled from AssemblyScript to WebAssembly, run on a *second* Worker that receives raw pixel data from the decode worker via `SharedArrayBuffer` (no `postMessage` copy of the pixel payload) — see [Optional blur filter](#optional-blur-filter)

This is a playback/processing pipeline, not a video editor — there's no encoding, export, or timeline-effects UI, by design.

## What's actually verified here

This README states only what was actually measured and tested for this project, not what "should" work. In particular:

- **Tested in three browser engines** (Chromium, Firefox, and WebKit — see [Browser support](#browser-support) below), but WebKit means Playwright's bundled WebKit build specifically, not Apple's shipped Safari.app.
- **Only tested against synthetic H.264-in-MP4 fixtures** generated by ffmpeg (see [Test fixtures](#test-fixtures)) — not real-world footage, not other codecs.
- Every benchmark number in this file is a real, reproducible measurement recorded during development (see `DECISIONS.md`), not an estimate — including one that isn't flattering: measured head-to-head, the WASM blur filter is consistently *slower* than the equivalent plain JavaScript, not faster (see [Optional blur filter](#optional-blur-filter)).

## Setup

```bash
npm install
npm run dev
```

Open the printed local URL, choose an MP4 file, and use the Play/Pause, Reverse, speed selector, and scrubber controls.

Requires Node.js (developed and tested with **v23.10.0** / npm **10.9.2**).

### Building for production

```bash
npm run build
npm run preview
```

Vite automatically code-splits the Web Worker (which holds the entire decode/render pipeline) into its own chunk, separate from the small main-thread bundle. The WASM blur module is compiled automatically (`npm run build:wasm`, wired into `predev`/`prebuild`/`pretest:unit` — no manual step needed) via the `assemblyscript` devDependency.

## Optional blur filter

A "Blur: Off/On" toggle applies a box blur to each displayed frame, computed by a WebAssembly module (compiled from AssemblyScript, `assembly/index.ts`) running on a **second** Worker (`src/processing-worker.ts`) — separate from the one that demuxes/decodes/renders. The two workers are linked by a direct `MessageChannel` the main thread sets up once and then steps out of, and share raw pixel data through a pair of `SharedArrayBuffer`s rather than copying it through `postMessage` — only small control messages (`{slot, frameSeq, format, ...}`) travel that way. Full architecture, the two real bugs found building it, and why `Atomics` was deliberately *not* used are in `DECISIONS.md`.

**Requirements:** `SharedArrayBuffer` only exists in a cross-origin-isolated context. `vite.config.ts` sets the required `Cross-Origin-Opener-Policy`/`Cross-Origin-Embedder-Policy` headers for `npm run dev`/`npm run preview`; a real deployment needs the hosting platform configured to send the same two headers, or the toggle hides itself automatically (feature-detected — core playback is unaffected either way, blur is purely additive).

**Pixel format handling:** `VideoDecoder`'s native output format turned out to differ by both browser *and* decode backend (hardware- vs. software-accelerated) even for the identical source file — I420 (Chromium, headless/software decode), NV12 (Chromium with hardware decode; also WebKit), BGRX (Firefox) were all observed. Rather than trust `copyTo()`'s own format-conversion option (confirmed unreliable — WebKit silently ignores it), the WASM module implements all three conversions itself. See `DECISIONS.md` for the measurements that led here.

**Performance, honestly:** measured head-to-head against an identical pure-JS reference implementation (same algorithm, `src/blur-reference.ts`), the WASM version is **consistently ~1.5x slower**, not faster — see [Measured benchmarks](#measured-benchmarks). The feature is a genuine, working demonstration of the technique (real WASM, real `SharedArrayBuffer`, real cross-worker sharing, verified in all three browser engines), not a demonstrated performance win.

## Browser support

WebCodecs support varies significantly across browsers and was not assumed to be universal — every claim below was actually tested, not inferred from spec compliance.

| Context | Engine | Version | Notes |
|---|---|---|---|
| Manual testing throughout development | Chromium | `Chrome/148.0.7778.280` | Claude Code's bundled Chromium-based preview browser (via `navigator.userAgent`) |
| Automated end-to-end tests (Playwright) | Chromium | `151.0.7922.34` | |
| Automated end-to-end tests (Playwright) | Firefox | `153.0` | |
| Automated end-to-end tests (Playwright) | WebKit | `26.5` | **Playwright's bundled WebKit build — not Apple's shipped Safari.app.** No way to drive real Safari interactively was available in the environment this was tested from; treat "WebKit-engine support confirmed" as the accurate claim, not "Safari confirmed." |

The full Playwright suite (`npm run test:e2e`) runs against all three engines by default and, as of the last test run, **passes identically in all three (21/21)** — full-file decode/playback, forward and backward keyframe seeking, reverse playback, and the bounded seek-cache behavior all work with zero code changes needed between engines. This was a real, if pleasant, surprise: an earlier assumption in this project's development notes had guessed Firefox/Safari WebCodecs support was weak or absent, which turned out to be wrong for the versions tested (see `DECISIONS.md`'s "Post-Stage-6 follow-up" entry for the full methodology).

The app feature-detects `VideoDecoder`, `Worker`, and `OffscreenCanvas` on load and shows an explicit message if any are missing, rather than failing silently or half-working.

## How the pipeline is built

- **`src/mp4-demuxer.ts`** — demuxes an MP4 `ArrayBuffer` via [mp4box.js](https://github.com/gpac/mp4box.js) into a `VideoDecoderConfig` and an array of `EncodedVideoChunk`s (no browser ships a native MP4 demuxer, so this dependency is required for a WebCodecs pipeline at all).
- **`src/frame-buffer.ts`** — a generic, cancellable FIFO queue used to decouple decoding from rendering.
- **`src/prefetch-controller.ts`** — pure logic that sizes the buffer's target depth from a one-time measured decode-fps vs. the file's nominal playback fps (floor 6 frames, ceiling 90).
- **`src/keyframe-index.ts`** — pure keyframe/GOP-boundary lookup logic backing seeking and reverse playback.
- **`src/gop-decoder.ts`** — decodes one bounded GOP range with a fresh decoder; shared by seeking and reverse playback.
- **`src/frame-cache.ts`** — a generic, capacity-bounded LRU cache.
- **`src/seekable-player.ts`** — ties all of the above together: `play()`/`pause()`/`seekTo()`/`setPlaybackRate()`/`setDirection()`, keyframe-based seeking with an LRU seek-frame cache, and GOP-buffered reverse playback.
- **`src/video-worker.ts`** — runs `SeekablePlayer` entirely inside a dedicated Worker against a transferred `OffscreenCanvas`, so demuxing, decoding, and rendering never touch the main thread.
- **`src/worker-video-player.ts`** / **`src/worker-protocol.ts`** — the main-thread proxy and shared message types for talking to the decode worker.
- **`assembly/index.ts`** — AssemblyScript source for the WASM YUV→RGBA conversions (I420/NV12/BGRX) and box blur; compiled to `build/blur.release.wasm`.
- **`src/blur-reference.ts`** — pure-TypeScript reference implementation of the identical algorithms; the correctness oracle the compiled WASM is tested against, and the JS side of the WASM-vs-JS benchmark.
- **`src/processing-worker.ts`** / **`src/pixel-mailbox.ts`** / **`src/pixel-processor-client.ts`** — the second Worker that runs the WASM blur, the `SharedArrayBuffer`-based message protocol between it and the decode worker, and the client class `SeekablePlayer` uses to talk to it.
- **`src/main.ts`** — wires the UI controls to `WorkerVideoPlayer`.

## Testing

```bash
npm run test        # unit tests (Vitest) + browser tests (Playwright), in that order
npm run test:unit   # Vitest only — pure logic: FrameBuffer, AdaptivePrefetchController, KeyframeIndex, FrameCache
npm run test:e2e    # Playwright only — real WebCodecs decode/render/seek in an actual browser
```

47 Vitest unit tests cover the pure, WebCodecs-independent logic (buffer backpressure/cancellation, adaptive buffer-depth math, keyframe/GOP lookups, LRU cache eviction, and the blur reference implementation — including a test that loads the *real compiled* `.wasm` module in Node and checks it matches the JS reference exactly, not a mock). 8 Playwright test specs run against real browser WebCodecs decoding — full-file playback for both fixtures, seek-lands-on-the-correct-frame (forward and backward), reverse playback producing monotonically decreasing timestamps, cache-hit behavior on repeat seeks, bounded memory growth across many seeks, and the blur filter visibly changing (and un-changing) the rendered frame — each run against all three browser engines (see [Browser support](#browser-support)), for 24 test executions. All 47 unit tests and all 24 Playwright executions pass.

## Test fixtures

No real-world sample footage was available while building this project, so all test fixtures are synthetic, fully reproducible ffmpeg output (SMPTE-style `testsrc` pattern + a tone), generated on demand rather than committed to git (`test-media/` is gitignored — regenerate with the commands below).

| File | Resolution | Duration | Profile | Purpose |
|---|---|---|---|---|
| `short_640x360_10s.mp4` | 640×360 | 10s | H.264 Constrained Baseline | Fast iteration / baseline correctness |
| `long_1920x1080_60s.mp4` | 1920×1080 | 60s | H.264 High | Higher-resolution decode throughput |
| `long_form_640x360_900s.mp4` | 640×360 | 900s (15 min) | H.264 Constrained Baseline | Long-form memory/eviction benchmark |

Regenerate all three:

```bash
mkdir -p test-media

ffmpeg -f lavfi -i "testsrc=duration=10:size=640x360:rate=30" \
  -f lavfi -i "sine=frequency=440:duration=10" \
  -c:v libx264 -pix_fmt yuv420p -profile:v baseline -level 3.0 -g 30 \
  -c:a aac -shortest test-media/short_640x360_10s.mp4

ffmpeg -f lavfi -i "testsrc=duration=60:size=1920x1080:rate=30" \
  -f lavfi -i "sine=frequency=220:duration=60" \
  -c:v libx264 -pix_fmt yuv420p -profile:v high -level 4.0 -g 30 \
  -c:a aac -shortest test-media/long_1920x1080_60s.mp4

ffmpeg -f lavfi -i "testsrc=duration=900:size=640x360:rate=30" \
  -f lavfi -i "sine=frequency=330:duration=900" \
  -c:v libx264 -pix_fmt yuv420p -profile:v baseline -level 3.0 -g 30 \
  -c:a aac -shortest test-media/long_form_640x360_900s.mp4
```

All three use a keyframe interval of 30 (`-g 30`, one keyframe/GOP boundary per second at 30fps). Only H.264-in-MP4 has been generated and tested; the demuxer/decoder-config code path also handles HEVC/VP9/AV1 generically (it reads whichever of `avcC`/`hvcC`/`vpcC`/`av1C` is present), but that path is unverified — no fixtures in those codecs have been tried.

## Measured benchmarks

All numbers below are real measurements taken during development (Claude Code Browser pane, `Chrome/148.0.7778.280`), recorded verbatim in `DECISIONS.md` alongside full methodology notes. None are estimates.

### Decode throughput and time-to-first-frame (adaptive buffering)

| Fixture | Decode throughput | Time to first frame | Adaptive buffer target |
|---|---|---|---|
| `short_640x360_10s.mp4` | 1764.7 fps | 143 ms | 90 frames (clamped to max) |
| `long_1920x1080_60s.mp4` | 1016.9 fps | 103 ms | 90 frames (clamped to max) |

Both fixtures decode at 30-60x real-time on the test hardware — read this as "this hardware/codec/synthetic-content combination," not a general H.264 decode-speed claim. Both clips played back with zero stalls and zero dropped frames.

### Seek latency (keyframe-based, forward and reverse)

| Fixture | Direction | Sample seeks | Latency range |
|---|---|---|---|
| `short_640x360_10s.mp4` | Forward | 2.00s, 5.00s, 9.00s | 23.7-32.1 ms |
| `short_640x360_10s.mp4` | Reverse | 3.00s, 1.00s, 7.00s | 29.7-31.6 ms |
| `long_1920x1080_60s.mp4` | Forward | 10.00s, 30.00s, 55.00s | 32.2-39.1 ms |
| `long_1920x1080_60s.mp4` | Reverse | 20.00s, 5.00s, 45.00s | 35.3-38.0 ms |
| `long_form_640x360_900s.mp4` | Both | spread across 900s | ~30 ms (unchanged) |

Every seek landed exactly on the requested frame. Latency is dominated by decoding one full GOP (≤30 frames) with a fresh decoder, not by resolution or file duration — a seek on the 900-second fixture is no slower than one on the 10-second fixture.

### Main-thread blocking, before vs. after moving to a Worker

Measured as cumulative `CanvasRenderingContext2D.prototype.drawImage` execution time on the main thread across a full playthrough (the Long Tasks API recorded zero >50ms tasks in *either* architecture, since WebCodecs decode dispatch doesn't block the calling thread by design — `drawImage` is the real, attributable per-frame main-thread cost).

| Fixture | Before (main-thread render) | After (Worker + OffscreenCanvas) |
|---|---|---|
| `short_640x360_10s.mp4` (300 frames) | 92.0 ms | **0.0 ms** (0 calls observed) |
| `long_1920x1080_60s.mp4` (1800 frames) | 430.3 ms | **0.0 ms** (0 calls observed) |

The "after" zero is structural, not a rounding artifact: the worker's rendering calls execute in a separate JS realm the main-thread instrumentation can't observe, which is the same reason the cost is actually eliminated from the main thread, not just hidden from this measurement technique.

### Long-form memory: bounded (LRU cache) vs. unbounded

Measured by issuing many `seekTo()` calls spread across the full 900-second long-form fixture and sampling the live open-`VideoFrame` count after each one — run twice with the identical code path, differing only in the seek-cache's capacity parameter (120, the real default, vs. 1,000,000, simulating the eviction policy switched off).

| Seeks issued | With eviction (120-frame cache) | Without eviction |
|---|---|---|
| 200 | **120** | 6,000 |
| 400 | **120** (unchanged) | 12,000 (doubled) |

With the eviction policy active, memory is flat regardless of session length. Without it, memory grows exactly linearly with usage, with no ceiling — the failure mode a real long-form scrubbing session would hit.

### WASM vs. JS for the blur filter's pixel processing

Measured by dynamically importing both the compiled `.wasm` module and the pure-JS reference implementation into the same page and timing repeated calls on identical pseudo-random pixel buffers (warm-up calls excluded). This measures the real, complete per-call cost including copying data into and out of WASM linear memory — exactly what the actual pipeline pays on every frame.

| Operation | Size | WASM mean | JS mean | Ratio (JS/WASM) |
|---|---|---|---|---|
| Box blur (radius 6) | 640×360 | 290.3 ms | 196.0 ms | 0.67× |
| Box blur (radius 6) | 1920×1080 | 2647.3 ms | 1797.2 ms | 0.68× |
| I420→RGBA conversion | 640×360 | 4.2 ms | 2.9 ms | 0.68× |

**WASM was consistently ~1.5x slower than plain JS**, not faster, across every function tested at both resolutions — reported as measured, per this project's rule against fabricating or rounding up performance claims. The likely cause (consistent with the near-identical ratio across very different data sizes): every WASM call here pays a fixed "bridge tax" copying the full buffer into WASM memory and back out, on top of the computation — a cost that scales with data size exactly like the computation does. A version operating directly on a shared `WebAssembly.Memory` (avoiding that copy) might close the gap; that's a real, untested hypothesis, not a claim made here.

## Known limitations

- No audio playback — only the video track is demuxed/decoded (the pipeline explicitly ignores audio tracks; this was in scope from the start, not a regression).
- Single video track only; files with multiple video tracks use the first one found.
- Real Safari.app is untested — only Playwright's WebKit build, which shares Safari's engine but isn't the actual shipped browser (see [Browser support](#browser-support)).
- Codecs other than H.264 are unverified (see [Test fixtures](#test-fixtures)).
- The seek/frame cache is scoped to `seekTo()` only — continuous forward/reverse playback doesn't use it, since it visits each frame position once, in order, with no repeat-access pattern for a cache to help with (see `DECISIONS.md`, Stage 5).
- The blur filter needs cross-origin-isolation headers to work at all (see [Optional blur filter](#optional-blur-filter)); untested on any real hosting platform, since this project has never been deployed anywhere.
- The blur filter is measurably slower in WASM than in plain JS for this implementation of this workload — see [Measured benchmarks](#measured-benchmarks). It's included as a working demonstration of the technique, not because it's faster.
